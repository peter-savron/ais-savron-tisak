# RawSpecIndex in ArcadeDB

Use the project’s pinned ArcadeDB 26.11.1 capabilities for [RawSpecIndex](../../features/RawSpecIndex.md). Published [RawSpec vertices](Spec.md) and their Git revisions remain the source of index input.

| Search | Index and representation |
| --- | --- |
| Exact identity | Use the existing source-scoped relative-path lookup. Preserve path case and punctuation. |
| Names and path terms | Use a FULL_TEXT index with BM25 on derived source name, basename and path terms once per RawSpec. Split segments and compound filenames into searchable terms and retain the original path. Rank basename matches higher. Use escaped literals for plain input and explicit token-prefix patterns for prefix search. Verify ordered path expressions against the original segments before applying the final result limit. |
| Content keywords | Apply BM25 to chunk text for the current lexical recipe and published revision. Group chunk hits by RawSpec UUID for document results. |
| Dense semantic search | Use LSM_VECTOR on ARRAY_OF_FLOATS with FLOAT32 by default. The engine also supports INT8 encoded vectors using BINARY. Choose explicit dimensions and the profile’s metric (cosine, dot product or Euclidean). Quantization is a separate index setting. |
| Learned sparse search | LSM_SPARSE_VECTOR accepts weighted dimension IDs from a sparse encoder. This is optional; BM25 operates directly on indexed text terms. |

A BM25 search for `payments` or `pay*` needs no embedding. A semantic search embeds query text with the same profile used to index the passages. The engine supports inferring dense dimensions from the first vector, but dimensions alone cannot identify the encoder. Two models of the same width can have incompatible vector spaces. [ArcadeDB index types](https://docs.arcadedb.com/arcadedb/concepts/indexes) and [full-text indexing and BM25](https://docs.arcadedb.com/arcadedb/how-to/data-modeling/full-text-index).

## Storage and recovery

Store one RawSpecIndex document per workspace, with a unique index on workspace UUID. Create the workspace document, RawSpecIndex document and first active configuration entry in the same transaction. Persist the workspace configuration changelog in ArcadeDB. Give each entry a unique (workspace UUID, revision ID) key and store its predecessor, immutable chunker selection and settings, and optional embedder selection and profile. The RawSpecIndex document references the active entry and its lexical and optional vector indexes. Load effective settings through that entry. Each migration and run references its target entry. Index profile, generation and migration IDs uniquely. Serialize activation with a conditional transaction that updates the pointer and records the transition together. Keep provider credentials in the secret facility. The database stores only their references.

Store chunks as vertices linked to their RawSpec. Key each occurrence by (workspace UUID, RawSpec UUID, publication revision, recipe version, ordinal). Store its offsets, text and content hash. Lexical search addresses the current lexical recipe; vector generations can reference the same chunk nodes when their recipes match.

Use a separate vector entry type and index per (workspace UUID, generation), with a unique entry per chunk occurrence. Store its chunk reference, expected hash, embedding type, profile ID, state and optional vector. Create the chunk and durable embedding work before the provider call. On failure, atomically persist NEEDS_REVIEW, the error and the generation’s STALE flag. Only READY vectors matching the expected revision, hash and profile qualify for search. Commit a successful retry conditionally on those same values. Recheck outstanding work transactionally before clearing STALE. Resolve the physical index exclusively from the authorized workspace and its generation. Apply the same partition boundary to sparse vectors, backfill, validation, cache keys and rollback. Candidate selection must stay inside that partition even when workspaces use identical profiles. Create vector storage only on explicit enablement. Maintain a workspace-scoped lexical index independently, including when no embedding configuration exists. Record indexing work durably with the publication transaction, including whole-source deletion before its metadata disappears. Apply access and current-revision checks before returning results. Stale passages must never make a deleted publication retrievable.

The existing startup schema changelog creates the stable control types and indexes. The workspace configuration changelog records owner-requested changes and their build, checkpoint, cutover and rollback events. Store migration attempts as documents with unique run IDs and a unique (workspace UUID, run sequence) index for latest-run lookup. Allocate the sequence and claim the attempt atomically. Fence abandoned workers before retrying. Record terminal results durably; successful cutover records the result in the pointer-switch transaction. A failed build can span restarts without replaying startup schema changes. Allow only the application’s storage service to mutate these records through supported interfaces. Embedded database files remain under the operating system account’s control; the journal does not prevent direct edits by an administrator with filesystem access.
